# 법적 고지사항(약관·사업자정보) 관리

> **이 문서의 `apps/backend/...` 경로와 `deploy-*-backend-ec2.yml` 워크플로우는 별도 레포 [`picake-engineering-backend`](https://github.com/picake-team/picake-engineering-backend)의 것입니다.** 로컬에서는 이 레포의 형제 폴더(`../picake-engineering-backend`)에서 확인하세요. `apps/web-*` 경로는 이 레포입니다.

통신판매업 신고번호 등 사업자정보는 그 자체로 독립된 데이터가 아니라 **약관(주로 이용약관 1조 부근·개인정보처리방침)의 필수 구성요소**로 노출됩니다. 그래서 "사업자정보 반영"과 "약관 반영"을 분리하지 않고 이 skill 하나로 다룹니다.

## 0. 원칙

- **절대 임의로 지어내지 않는다.** 사업자등록번호, 고객센터 연락처(전화/이메일), 대표자명, 주소, 통신판매업 신고번호처럼 실제 값이 필요한 항목은 근거 문서(사업자등록증·통신판매업신고증 등, 보통 `.claude/exchange.md`에 사용자가 이미지 경로를 남겨둠) 또는 사용자 답변으로만 채운다. 근거가 없으면 사용자에게 직접 물어본다 — 특히 법적 문서이므로 잘못된 연락처/번호를 게시하면 실제 법적 리스크가 된다.
- **민감정보는 공개 문서에 넣지 않는다.** 통신판매업신고증에는 대표자 생년월일, 문서확인번호(정부24 진본확인용) 같은 항목이 함께 나오는데, 이건 신고 사실을 증명하는 용도일 뿐 법정 고지 의무 항목이 아니다. 공개 약관/사업자정보에는 상호·대표자명·주소·통신판매업신고번호·사업자등록번호·연락처만 사용한다.
- **"최소한이지만 누락 없이"가 목표.** 표준약관을 통째로 베끼면 실제 서비스에 없는 기능(예: 안 쓰는 결제수단, 없는 멤버십/포인트 제도)에 대한 조항이 남아 오히려 사실과 다른 약관이 된다. 반대로 짧게 쓰겠다고 법정 필수 고지사항을 빼면 안 된다. 아래 2번 체크리스트가 하한선이다.
- **약관은 실제 구현을 따라간다.** 조항을 쓰기 전에 해당 기능이 코드에 실제로 있는지 먼저 확인한다 (예: 결제 방식, 제3자 제공 여부, 위치기반서비스 여부). 확신이 없으면 관련 모듈을 검색해서 사실을 확인한 뒤 쓴다.

## 2. 문서 타입별 법정 최소 요건

`apps/backend/src/modules/terms/constants/terms.constants.ts`의 `TermsType` 6종 기준. 각 타입을 쓰기 전에 해당 조항이 실제 기능과 맞는지 코드에서 먼저 확인한다.

- **CONSUMER_TERMS_OF_SERVICE (구매자 이용약관)** — 전자상거래법 표준약관 골격: 목적, 용어정의, 사업자정보 고지(1번 표), 서비스 제공/변경/중단, 회원가입·탈퇴, 예약(계약) 성립, **대금 결제 — 실제는 PG가 아니라 계좌이체(무통장입금) 방식**(`apps/backend/src/modules/order` — `PAYMENT_PENDING`/`PAYMENT_COMPLETED` 상태, 스토어 정산 계좌로 직접 입금), 청약철회·환불 절차, 서비스 이용제한, 면책조항, 분쟁해결/관할법원. 카드결제 PG를 쓰는 것처럼 쓰지 말 것 — 실제로 없다.
- **CONSUMER_PRIVACY_POLICY (구매자 개인정보처리방침)** — 개인정보보호법 필수 항목: 수집 항목/목적(전화번호, 소셜로그인 식별자 — Google/Kakao/Apple, 위치정보), 보유기간, 제3자 제공 여부, 처리위탁 업체 명시(알림톡·SMS 발송 위탁사 — SOLAPI, 푸시 발송 — Firebase, 파일 업로드 — AWS 등 실제 연동된 업체만), 이용자 권리(열람·정정·삭제), 파기절차, 안전성 확보조치, 개인정보보호책임자 지정(이름/연락처 — 대표자로 지정 가능), 열람청구 접수·처리 부서.
- **CONSUMER_THIRD_PARTY_CONSENT (제3자 제공 동의)** — 실제로 개인정보를 제3자에게 "제공"(위탁이 아니라 제공)하는 사례가 있는지 먼저 확인. 없다면 이 타입 자체를 활성화하지 않거나("현재 서비스는 이용자의 개인정보를 제3자에게 제공하지 않습니다") 최소 문구만 남긴다 — 없는 제공을 있는 것처럼 쓰면 오히려 위법 소지.
- **CONSUMER_LOCATION_TERMS (위치기반서비스 이용약관)** — `apps/web-user/src/features/store/components/map` 등 지도 기반 스토어 탐색 기능이 실제로 있음. 단, 위치정보의 보호 및 이용 등에 관한 법률상 **위치정보사업자/위치기반서비스사업자 신고**가 별도로 필요할 수 있음 — 이 skill로 작업하기 전 사용자에게 해당 신고 여부를 확인. 신고 전이면 "정밀 위치정보를 수집하지 않는다"/"단순 근처 매장 표시만 제공한다" 등 범위를 신고가 필요 없는 수준으로 명확히 제한하는 문구로 조정.
- **SELLER_TERMS_OF_SERVICE (판매자 이용약관)** — 입점 판매자 대상. Picake(두루랩스)가 **통신판매중개자**인지 직접판매자인지 명확히 밝힌다(실제 구조: 각 스토어=판매자가 자체 정산 계좌로 직접 입금받는 구조이므로 통신판매중개자에 가까움 — `apps/backend/src/modules/store`의 `bankAccountNumber`/`accountHolderName`이 스토어별로 존재). 정산 계좌 등록·수수료 정책이 실제로 있으면 명시, 없으면 없다고 쓰거나 언급하지 않는다.
- **SELLER_PRIVACY_POLICY (판매자 개인정보처리방침)** — 위 개인정보처리방침과 동일 골격, 대상만 판매자(사업자등록번호, 정산 계좌 등 판매자가 제공하는 항목 포함).

## 3. 작성 후 자가 점검 (필수, 생략 금지)

각 문서를 다 쓴 뒤 아래 3가지를 순서대로 점검하고 결과를 사용자에게 요약 보고한다.

1. **약관과 실제 구현이 다른 부분** — 조항에 쓴 기능이 코드에 실제로 존재하는지 하나씩 대조 (결제수단, 환불 절차, 위치기반서비스 범위, 제3자 제공 여부 등).
2. **과하게 작성된 내용** — 표준약관을 그대로 가져오면서 Picake에 없는 기능(포인트/멤버십, 정기결제, 해외이전, PG사 개인정보 제공 등)에 대한 조항이 남아있지 않은지.
3. **누락된 내용** — 2번 체크리스트 대비 빠진 법정 필수 항목이 없는지 (특히 개인정보처리방침의 9개 필수 항목, 이용약관의 사업자정보 고지).

## 4. DB 반영

- 약관은 **수정이 아니라 항상 새 버전 등록**이다 (`terms-write.service.ts` 정책 — 기존 레코드는 절대 변경하지 않음). 첫 실 데이터 반영이라도 스테이징/프로덕션에 이미 placeholder 시드(버전 1.0, "시드 데이터용 약관 본문입니다")가 들어있을 수 있으므로, 반영 전 `GET /v1/admin/terms/versions?type=<TYPE>`로 기존 버전을 확인하고 다음 버전 번호(예: 1.0이 있으면 1.1)를 정한다.
- 엔드포인트: `POST /v1/admin/terms` — body `{ type, version, title, content, effectiveAt, activateNow: true }`. `activateNow: true`면 같은 타입의 기존 활성 버전이 자동 비활성화된다.
- **API 전역 prefix는 `/v1`이다** — `/admin/terms`가 아니라 `/v1/admin/terms`. base URL: production `https://api.picakes.com`, staging `https://api-staging.picakes.com`.
- **관리자 인증은 절대 대신 로그인 시도하지 않는다.** admin 로그인은 ID/PW + Google OTP가 필수라 자동화 토큰이 없다(`picake-data-report` skill과 동일 정책). 사용자에게 해당 환경의 유효한 관리자 Bearer 토큰을 요청한다 — web-admin에 로그인 후 브라우저 개발자도구 → localStorage 또는 네트워크 탭에서 확인 가능하다고 안내.
- **순서: staging 먼저 반영 → 사용자에게 확인/승인 → production 반영.** 프로덕션 반영은 실제 서비스 이용자에게 노출되는 법적 문서이므로, 사용자의 명시적 승인 없이 진행하지 않는다.
- 반영 후 `GET /v1/admin/terms`(활성 버전 목록)로 각 환경에서 정상 반영됐는지 확인한다.
