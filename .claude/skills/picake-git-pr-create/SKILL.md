# PR 생성

`gh` CLI로 GitHub Pull Request를 생성합니다. PR 생성은 다른 사람에게 보이는 행동이므로, 마지막에 반드시 사용자 확인을 받은 뒤에만 실행합니다.

## 1. 매번 사용자에게 확인할 것

아래 2가지는 코드나 커밋에서 추론하지 말고 **매번 사용자에게 직접 질문**합니다 (AskUserQuestion 사용).

1. **브랜치**: 어느 브랜치(head)에서 어느 브랜치(base)로 머지할지
   - 현재 브랜치를 head 후보로 보여줄 수는 있지만, 그것이 맞는지는 반드시 확인받습니다.
2. **담당자(assignee)**: PR 담당자로 지정할 GitHub 아이디

이 2가지가 명확해지기 전까지 커밋/파일 분석이나 PR 생성으로 넘어가지 않습니다. 그 외에 애매한 부분(예: base 브랜치에 이미 올라간 변경까지 포함해야 하는지 등)이 있으면 추가로 사용자에게 물어봅니다.

## 2. 브랜치 상태 확인

```bash
git status
git fetch origin
git log <base>...<head> --oneline
git diff <base>...<head> --stat
```

- head 브랜치에 로컬에만 있고 원격에는 없는 커밋이 있으면, push가 필요하다는 것을 사용자에게 알리고 확인받은 뒤 `git push -u origin <head>`를 실행합니다. 원격 push는 임의로 하지 않습니다.
- head/base 브랜치가 로컬에 없으면 origin 기준으로 존재하는지 확인합니다.

## 3. PR 제목 자동 작성

`git log <base>...<head>`와 변경 파일을 분석해서 아래 규칙으로 제목을 직접 작성합니다 (사용자에게 묻지 않음).

```
[APP1,APP2][TYPE]: 설명
```

- **APP**: [[picake-git-commit-convention]] skill과 동일한 기준으로 판단 (`git diff <base>...<head> --stat`로 변경 경로 확인)
  - `WEB-USER` (`apps/web-user`), `WEB-SELLER` (`apps/web-seller`), `WEB-ADMIN` (`apps/web-admin`), `COMMON` (특정 앱에 한정되지 않는 변경)
  - 여러 앱에 걸친 변경이면 콤마로 나열 (예: `[WEB-USER,WEB-SELLER]`)
- **TYPE**: 변경 내용의 성격에 맞게 하나 선택
  - `ADD` (새 기능), `UPDATE` (기존 기능 개선/변경), `FIX` (버그 수정), `REFACTOR` (리팩토링), `REMOVE` (삭제), `DOCS` (문서), `CHORE` (빌드/설정/의존성)
- **설명**: 한국어로, 이 PR이 무엇을 하는지 간결하게 (커밋이 여러 개면 전체를 아우르는 요약)
- 커밋이 하나뿐이고 이미 이 형식을 따른다면 그 커밋 메시지를 그대로 제목으로 써도 됩니다.

## 4. PR 본문 자동 작성 (고정 레이아웃)

본문 내용은 매번 커밋/diff를 분석해서 직접 채우되, **아래 레이아웃 구조는 이 skill을 쓸 때마다 항상 동일하게 유지**합니다.

```markdown
## 📋 요약

<이 PR이 무엇을 하는지 1~3문장>

## ✨ 주요 변경사항

- [APP] 변경 내용 1
- [APP] 변경 내용 2

## 🧪 테스트 계획

- [ ] 확인이 필요한 항목 1
- [ ] 확인이 필요한 항목 2

## 📎 참고 사항

<리뷰어가 알아야 할 특이사항, 주의사항, 마이그레이션 등. 없으면 이 섹션 자체를 생략>
```

- "주요 변경사항"은 커밋 단위 또는 의미 단위로 묶어서 정리 (커밋 메시지 나열이 아니라 요약).
- "테스트 계획"은 변경 내용에 맞춰 실제로 확인해야 할 항목을 판단해서 작성 (예: 특정 화면 동작 확인, staging 배포 후 확인 등).
- "참고 사항" 섹션은 정말 알릴 내용이 있을 때만 포함합니다.

## 5. 생성 전 최종 확인 (필수)

`gh pr create` 실행 전에 아래를 사용자에게 보여주고 명시적으로 확인받습니다.

- base ← head 브랜치
- 담당자
- 제목
- 본문 전체

확인받은 뒤에만 아래를 실행합니다.

```bash
gh pr create --base <base> --head <head> --title "<제목>" --assignee "<담당자>" --body "<본문>"
```

- 본문은 개행이 많으므로 `--body-file`로 임시 파일을 만들어 전달하는 것을 권장합니다 (따옴표/이스케이프 문제 방지).
- 생성 후 PR URL을 사용자에게 알려줍니다.
