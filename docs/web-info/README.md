## 🧭 설계 원칙

- **휴대폰·PC 둘 다, 글은 한 벌입니다(2026-11-20).** 같은 주소·같은 글을 화면 폭에 따라 배치만 바꿉니다. 폭 구간은 `src/common/constants/screen.constants.ts` 한 곳(휴대폰 ~767, PC `md` 768~, 넓은 PC `lg` 1024~)이고 `tailwind.config.ts`의 `screens`가 이 값을 씁니다. Next.js는 서버에서 먼저 그리므로 JS 폭 훅을 쓰지 않고 CSS(tailwind 반응형)로만 나눕니다(깜빡임 없음). 휴대폰용·PC용 화면을 따로 만들지 않아 검색·AI가 같은 글을 한 번 읽습니다(h1 하나). 사장님 웹의 "휴대폰·PC 나누는 원칙"([프로젝트 구조 - 가이드](../common/structure/프로젝트%20구조%20-%20가이드.md))과 같은 경계예요.
- **문서 전체가 스크롤됩니다.** 예전의 640px 스크롤 칸(`#root-scroll-container`)을 없앴습니다. 위쪽 줄은 `sticky`, 휴대폰 아래 주 버튼(`StickyCta`)은 `fixed`이고, 칸 이동이 위쪽 줄에 가리지 않게 `globals.css`의 `scroll-padding-top`이 위쪽 줄 높이(휴대폰 56·PC 72)보다 8px 큽니다. 스크롤 막대는 휴대폰에서만 숨깁니다.
- **소개 페이지 부품은 `src/common/components/landing`에 모읍니다.** 위쪽 줄(`SiteHeader`: 휴대폰 로고·작은 링크, PC 주 버튼, 넓은 PC 칸 이동 메뉴와 지금 칸 주황 밑줄), 첫 화면(`PhotoHero`: PC는 어두운 사진 + 흰 글자로 글 왼쪽, 휴대폰은 `phone-hero.ts`의 밝은 사진 아래 흰 바탕에 진한 글자. 두 사진은 `<picture>`로 폭에 맞는 한 장만 받는다), 칸 부품(`Blocks`: 제목·고민 칸·해결 줄·"이것도 돼요"·왼쪽 제목 칸·자주 묻는 질문·마지막 칸), 컴퓨터 화면 그림(`Shots`의 `PcShot`)과 사용법 영상(`ShotVideo`, 틀 모양은 `landing.styles.ts`의 `PHONE_FRAME`·`PC_FRAME`), 버튼(`Buttons`), 맨 아래(`SiteFooter`), 휴대폰 아래 주 버튼(`StickyCta`). 모양 값은 `landing.styles.ts`. 한 페이지에만 있는 칸은 `features/<쪽>/components`(사장님 `SellerSections`: 비교표·AI 칸·글|PC 화면·PC 화면 넘기기·처음 시작·0원).
- **web-user와 같은 구성을 따릅니다.** PostHog, 환경 판별(`NEXT_PUBLIC_NODE_ENV`), `robots`/`sitemap` 규칙이 web-user와 같습니다. 정적 소개 페이지라 Sentry는 쓰지 않습니다.
- **필요한 공용 코드만 복사해 씁니다.** 폰트 등은 web-user에서 복사한 것이며 web-user를 수정하지 않습니다. 원본이 바뀌어도 자동으로 따라가지 않습니다.
- **소개 페이지 그림은 실제 화면과 사진만 씁니다.** 휴대폰 화면은 로컬 예시 가게(테스트 DB "달콤스토어")를 눌러 녹화한 사용법 영상(아래)이고, PC 화면 그림(`pc-*.png`, 1440 폭)은 로컬 서버의 심사용 예시 가게를 "달콤스토어"로 보이게 해 찍은 것이고(개발 도구 단추·네이버 안내 줄은 숨김, 2026-11-20), 케이크 사진은 Unsplash·Pexels 무료 사진입니다(`features/seller/assets`, 출처는 페이지 파일 주석). 그림·아이콘·빛번짐으로 꾸미지 않습니다(운영자가 "AI가 만든 느낌"이라고 함). 화면이 바뀌면 picake-hq skill `picake-marketing-image`의 스토어 스크린샷 방법으로 다시 찍습니다. 사용법 영상도 같은 원칙입니다(아래).
- **디자인 값은 web-user와 같이 씁니다.** 색·글자 크기·모서리·움직임은 공통 패키지 `@picake/design-tokens`의 손님 화면 preset입니다(`tailwind.config.ts`의 `presets`, 2026-11-08 복사본에서 바꿈). 패키지 값이 바뀌면 web-info도 따라 바뀝니다.
- **콘텐츠는 코드에 직접 작성합니다.** 문구를 고치려면 PR이 필요합니다.

## ✅ 소개 페이지를 만들 때 보는 것

소개 페이지는 DM·검색·AI 답변으로 처음 만나는 곳이라 보기 좋은 것만으로는 부족합니다. 만들기 전에 아래 기준을 세우고, 올리기 전에 하나씩 확인합니다(2026-11-14 운영자 요청).

| 기준        | 확인할 것                                                                                                                                                                                                                                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 설득        | 읽는 사람이 실제로 한 말(설문·방문·DM) 순서로 내세운다. 문장마다 지금 코드와 대조한 사실만 쓰고, 없는 숫자·후기는 쓰지 않는다. 주요 행동(버튼)은 하나                                                                                                                                                       |
| 검색(SEO)   | 사람이 검색할 말(예: 주문제작 케이크·예약·견적)과 한글·영문 이름(픽케이크·Picake)이 `title`·`description`·`h1`에 있다. canonical, `sitemap.ts`의 `lastModified`(내용을 크게 바꾸면 날짜도), 상용만 열린 `robots`                                                                                            |
| AI 검색     | 설명 첫 문장이 "픽케이크는 …예요" 한 문장 정의. 구조화 데이터(`JsonLd`, Organization·WebPage·Service), `public/llms.txt`를 페이지 내용과 같게. AI·검색 로봇이 본문을 읽는지 `curl -A "GPTBot"`·`"Yeti"`로 확인                                                                                              |
| DM 미리보기 | `openGraph` 제목·설명·그림을 그 페이지를 받을 사람에 맞게. 카카오톡·인스타그램은 PNG만 보여 준다                                                                                                                                                                                                            |
| 속도        | 첫 화면 사진(LCP)은 `priority`와 `fetchPriority="high"`. Lighthouse 모바일·PC를 각각 3번 돌려 중간값으로 LCP 2.5초 안을 본다(첫 회는 튈 수 있음). 영상은 첫 화면 아래 칸에만, 포스터 그림 + 가까이 올 때 받기(`ShotVideo`)                                                                                  |
| 접근성      | 확대를 막지 않는다(레이아웃 viewport). 글자 대비 4.5:1, 그림 `alt`(꾸밈 사진은 빈 값). 예외: 입점 버튼(주황 바탕 흰 글자)·첫 화면 머리말·0원·칸 머리말과 제목 속 강조 낱말(메인 주황)은 대비가 낮다는 것을 알고 운영자가 고른 색(2026-11-17·20). 비교표는 휴대폰에서 칸을 쌓아도 표로 읽히게 `role="table"` |
| 신뢰        | 운영사·연락할 곳이 보인다                                                                                                                                                                                                                                                                                   |
| 폭          | 320·390·768·1024·1280·1440 폭에서 옆으로 넘치지 않고 겹치지 않는지 위에서 아래까지 찍어 본다. 휴대폰은 아래 주 버튼이 첫 화면·마지막 칸·맨 아래에서 숨는지, 넓은 PC는 칸 이동 메뉴의 지금 칸 표시가 따라오는지                                                                                              |

- **파일**: `public/videos/seller/*.mp4`·`public/videos/customer/*.mp4`(H.264·소리 없음·faststart, 휴대폰 780×1120 = 화면 390×560의 2배, PC 1440×820, 한 개 0.2~0.67MB). 포스터는 `src/features/<쪽>/assets/video-*.jpg`로 **그 칸을 가장 잘 보여 주는 장면**이고, 재생도 그 장면(`start`초)부터 합니다. 영상을 바꾸면 페이지의 `VIDEO` 주소 `?v=`를 **꼭** 올립니다(`/videos/*`는 `next.config.ts`에서 1년 캐시라 안 올리면 옛 영상이 보입니다).
- **동작(`ShotVideo`)**: 처음에는 포스터 그림만 받고(첫 화면 속도 그대로), 칸이 반 넘게 0.3초 이상 보이면 영상을 받아 포스터 장면부터 재생하고(빨리 지나가면 받지 않음), 벗어나면 멈춥니다. 자동 재생이 막히면(아이폰 저전력 모드 등) 재생 표시가 뜹니다. 휴대폰 "동작 줄이기"·데이터 절약이면 포스터만 두고 누를 때 재생합니다. 화면을 누르면 멈춤·다시 재생, 멈춰 있으면 오른쪽 아래에 재생 표시가 뜹니다. 화면 읽기 프로그램은 포스터의 `alt`(영상에서 하는 일)를 읽습니다. 휴대폰 틀 폭은 PC 280px(영상 화면 전체가 칸 높이 460px 안에), 휴대폰 240px.
- **찍는 법**: picake-hq skill `picake-marketing-image`의 "사용법 영상". 로컬 테스트 서버의 예시 가게(달콤스토어)를 Playwright로 눌러 가며 2배 화면을 찍고(누르는 곳에 회색 점), 기다린 시간은 잘라 내고, 사장님 → 손님 화면은 흰색으로 잇고, ffmpeg로 묶습니다.
- **지킬 것**: 실제 화면만(꾸민 그림·글자 얹기 없음). 가게·손님·주문은 예시(연락처 010-0000-0000). **AI 결과는 실제 AI가 낸 것만**: 카톡 대화 읽기는 같은 대화를 실제 AI가 읽은 결과(backend `AI Draft Smoke` 2026-11-19)이고, 로컬에 AI 키가 없어 상품 설명 "AI로 쓰기"는 누르지 않았습니다. 네이버 연결 안내 줄은 가립니다(네이버 가져오기는 내세우지 않음, 법무 점검표 18). 손님 견적 영상은 "꼭 물어볼 가게" 검색에 카카오의 실제 가게 이름이 떠서 그 단계를 넘기고, 내 사진 AI 읽기(실제 결과 없음)도 찍지 않았습니다(디자인 모음 사진은 미리 정리된 설명이라 AI를 부르지 않음). 상용에 없는 모습을 찍지 않습니다 — 녹화에서 이상한 장면이 보이면 실제 화면 동작인지 먼저 잽니다(2026-11-24 상품 등록 영상에서 사장님 PC 창 버그를 찾아 11-25에 고친 뒤 사이즈 창 장면으로 다시 찍음). 운영·staging 계정은 쓰지 않습니다. **판매자·손님 앱의 그 화면이 바뀌면 그 칸 영상도 다시 찍습니다.**

## 📊 분석·모니터링

- PostHog는 web-user·web-seller와 **같은 프로젝트**를 쓰고, 이벤트에 `app: "web-info"`·`environment` 속성을 붙입니다. 기존 리포트·루틴은 `app` 필터를 걸고 있어 web-info 이벤트가 섞이지 않습니다.
- `info.picakes.com`과 `picakes.com`은 같은 상위 도메인이라 PostHog 방문자 식별자가 공유됩니다(`cross_subdomain_cookie` 기본값).
- 배포 결과는 다른 웹 앱과 같은 Discord 웹훅으로 가며, 알림 제목에 `web-info`가 표시됩니다.

## 🚀 개발·배포

```bash
yarn web-info:dev      # 개발 서버 (포트: 3004)
yarn web-info:build    # 빌드
yarn workspace @picake/web-info test   # CI 검사와 동일 (next build, 타입 검사 포함)
```

- 배포: `web-info/staging-*`, `web-info/production-*` 태그 푸시 → GitHub Actions → Vercel
- 도메인: 검증 `info-staging.picakes.com`, 상용 `info.picakes.com`
- 환경변수: `NEXT_PUBLIC_NODE_ENV`, `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST`

자세한 배포 설정은 [Vercel 배포 가이드](../infra/vercel/Vercel%20배포%20-%20가이드.md)를 참고하세요.

## ⚠️ 알아둘 점

- 오프라인 QR은 `https://picakes.com/partner`(web-user)를 가리킵니다. 2026-11-25부터 이 주소는 중간 화면 없이 `/seller/about?utm_source=partner_gate&utm_medium=offline&utm_campaign=qr`로 보냅니다(web-user `next.config.ts` redirects, 임시 307). hq 방문 리포트·데이터 리포트가 이 `utm_source`로 "QR"을 셉니다. 이 주소와 `/partner/about` 리다이렉트는 web-user에서 관리하므로 함부로 없애지 마세요.
